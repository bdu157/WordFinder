# 카메라 OCR 1단계 설계

작성일: 2026-08-19 · 대상: PLAN.md §8 로드맵 0~3주차의 카메라·OCR 파이프라인 첫 단계

## 1. 범위

카메라로 단어를 찍으면 **인식된 단어 목록이 바텀시트에 뜨는 것**까지 만든다.

지금 `CameraMock.recognizedWords`에 하드코딩된 단어 4개를 실제 OCR 결과로 교체하는 것이 목표다. 사전 조회는 이 범위에 없다 — 서버(Cloud Functions)가 아직 없고, `DictEntry` 계약도 확정 전이다. 서버 없이 끝까지 완성 가능한 범위로 잘랐다.

### 범위 밖

- 사전 조회, 단어 상세 시트의 실제 데이터 (`WordDetailSheet`은 계속 목업)
- 표제어 추정 (`running` → `run`) — PLAN.md F4에 따라 서버 몫
- 히스토리 저장, 크롭 썸네일
- 토치(플래시) 실제 동작

## 2. 결정 사항

| 항목 | 결정 | 근거 |
|---|---|---|
| 인식 엔진 | VisionKit `DataScannerViewController` | §3 |
| 교체 가능성 | `TextRecognizer` 프로토콜 뒤에 격리 | §3 |
| 확정 방식 | 스캔 버튼으로 시작 → 텍스트 안정되면 자동 확정 | §4 |
| 안정 판정 | 정규화 문자열이 0.6초 유지 | §5 |
| 타임아웃 | **7초** 후 대기 상태 복귀 + 안내 (실기기 튜닝, 원안 10초) | §5 |
| 권한 요청 시점 | **앱 실행 직후** — 카메라 화면이 뜰 때 (원안은 최초 Scan 탭 시였으나 VisionKit 동작상 불가, §6) | §6 |
| 단어 분리 | 클라이언트에서 임시 처리, 서버 붙으면 삭제 | §3 |

## 3. 구조

```
CameraView (SwiftUI)
  ├─ ScannerViewRepresentable ── DataScannerViewController
  │     가이드 박스 영역만 regionOfInterest로 지정
  │     자체 하이라이팅은 끄고 기존 오버레이를 그대로 사용
  │
  ├─ 기존 오버레이 유지: GuideMaskShape · CornerBracketsShape · topBar
  ├─ 하단 스캔 버튼 (신규)
  │
  └─ ScanViewModel  @Observable
        ├─ TextRecognizer (프로토콜)  ◄── 교체 지점
        │     └─ DataScannerRecognizer
        ├─ StabilityDetector   순수 로직
        └─ WordTokenizer       순수 로직 · 임시
```

### 책임

| 조각 | 하는 일 | 의존 |
|---|---|---|
| `TextRecognizer` | 박스 안에 보이는 텍스트를 계속 흘려보냄 | 프로토콜 — 카메라 구현에 무관 |
| `StabilityDetector` | 흘러오는 텍스트를 보다가 충분히 안 바뀌면 확정 신호 | 없음 (순수) |
| `WordTokenizer` | 확정 문자열을 `[ScannedWord]`로 분리 | 없음 (순수) |
| `ScanViewModel` | 셋을 연결하고 화면 상태 관리 | 위 셋 |
| `CameraView` | 그리기 | `ScanViewModel` |

### DataScanner를 고른 이유

카메라 세션·초점·연속 인식·프레임 관리가 전부 내장이라, 우리가 붙일 코드는 관심 영역 지정과 결과 수신뿐이다. `AVCaptureSession` + `VNRecognizeTextRequest`를 직접 구성하면 세션 생명주기·방향·스레딩·프레임 백프레셔·토치를 모두 직접 관리해야 하고, 그 대부분은 Apple이 이미 DataScanner에 넣어둔 것을 다시 만드는 일이다.

단점은 픽셀 버퍼에 접근할 수 없어 작은 글씨 확대나 대비 보정 같은 전처리를 넣을 수 없다는 것이다. 인식률이 부족하면 손댈 여지가 없다.

그래서 **`TextRecognizer` 프로토콜 뒤에 격리한다.** PLAN.md §8은 DataScanner와 AVFoundation+Vision의 인식률을 비교해 고르라고 하지만, 실제로 비교하려면 어차피 실기기에서 진짜 텍스트를 찍어야 한다. DataScanner는 빠르게 동작하는 상태에 도달하므로 **그것을 만들어 써보는 것 자체가 PoC**가 된다. 부족하다고 판명되면 구현체만 갈아끼우고 `StabilityDetector`·`WordTokenizer`·화면은 건드리지 않는다.

### 단어 분리가 임시인 이유

PLAN.md F4는 토큰화와 표제어 추정을 서버 몫으로 정해뒀다. 지금은 서버가 없으므로 클라이언트에서 공백·구두점 기준으로만 쪼갠다. 어려운 부분(`running` → `run`)은 **클라이언트에 넣지 않는다.**

`WordTokenizer`를 별도 파일로 격리하는 이유가 이것이다. 서버 F4가 붙으면 통째로 삭제한다.

## 4. 상태 흐름

```
  idle ──[Scan]──► scanning ──[0.6초 안정]──► settled
    ▲                  │                         │
    │                  │ [Cancel] 또는 [타임아웃]  │ [시트 닫힘]
    └──────────────────┴─────────────────────────┘
```

| 상태 | 카메라 | 인식 | 하단 버튼 | 캡션 |
|---|---|---|---|---|
| `idle` | 프리뷰 보임 | 안 함 | `Scan` | "Line up a word inside the box" |
| `scanning` | 프리뷰 보임 | 진행 중 | `Cancel` | 현재 인식 중인 텍스트 |
| `settled` | 프리뷰 보임 | 멈춤 | 숨김 | 시트 |

`idle`에서도 프리뷰와 가이드 박스는 보인다 — 버튼을 누르기 전에 미리 조준할 수 있어야 한다. 인식만 돌리지 않는다. 배터리와 발열에도 유리하다.

`settled`에서 프리뷰를 계속 살려두는 이유는 시트가 `.medium` 디텐트라 뒤가 보이기 때문이다. 인식 결과만 무시한다.

브래킷 색이 상태에 따라 바뀌는 로직은 `CameraView`에 이미 있다. 그대로 쓴다.

### 스캔 버튼이 필요한 이유

자동 확정만으로는 "지금은 인식하지 마"를 표현할 수단이 없다. 버튼이 게이트가 되면서 두 가지가 해결된다.

- 의도하지 않은 순간에 시트가 튀어나오지 않는다
- 시트에서 단어를 고르는 동안 새 인식이 끼어들지 않는다

부수 효과로, 시트를 닫으면 어차피 `idle`로 돌아가므로 "직전 확정 텍스트를 기억해 재발화를 막는" 로직이 불필요해진다.

버튼 위치는 하단 중앙이다. 시트가 올라오는 자리와 겹치므로 `settled`에서는 숨긴다.

## 5. 안정 판정과 타임아웃

OCR은 매 프레임 조금씩 다르게 읽는다. `resilient` → `Resilient` → `resilient ` 같은 흔들림이 있어서, **정규화 후 비교**하지 않으면 영원히 확정되지 않는다.

1. 인식 문자열 정규화 — 앞뒤 공백 제거, 소문자, 연속 공백을 하나로
2. 정규화 결과가 직전과 같으면 타이머 유지, 다르면 리셋
3. 같은 값이 **0.6초** 유지되면 확정
4. 2글자 미만은 무시 (노이즈)

`DataScannerViewController`는 텍스트 신뢰도 점수를 주지 않는다. 그래서 "얼마나 확실한가" 대신 **"얼마나 오래 같은가"** 로 판정한다. 손에 든 폰은 흔들리므로, 안정적으로 읽힌다는 것 자체가 좋은 신호다.

### 타임아웃

`scanning`에서 확정 조건이 영영 충족되지 않을 수 있다 — 박스 안에 글자가 없거나, 너무 작고 어두워 매 프레임 다르게 읽히거나, 손이 계속 흔들릴 때다. 이러면 사용자는 버튼을 눌렀는데 아무 일도 일어나지 않는 상태에 갇힌다.

**7초** 안에 확정하지 못하면 `idle`로 돌아가면서 안내를 띄운다: `"Couldn't read that — try moving closer"`.

타임아웃의 진짜 가치는 자동 복귀가 아니라 **이 안내 문구**다. 취소 버튼이 있으면 사용자가 직접 빠져나올 수는 있지만 왜 안 되는지는 모른다. PLAN.md §9는 OCR 정확도를 높은 리스크로 잡고 대응책을 "크롭 확대 유도 UX"로 적어뒀는데, 이 안내가 그 역할을 한다.

부수적으로 배터리도 아낀다 — 인식은 뉴럴 엔진을 계속 돌린다.

**0.6초 · 7초 · 2글자는 실기기에서 튜닝한 값이다** (§9). 원안의 타임아웃 10초는 안내가 뜨기까지 너무 오래 기다린다는 피드백으로 줄였다. 최소 길이는 `WordTokenizer.minimumLength` 쪽만 앱 경로에서 살아 있다.

## 6. 예외 처리

**카메라 권한** — 권한 요청은 **앱 실행 직후, 카메라 화면이 뜰 때** 일어난다. 원안은 "최초 Scan 탭 시"였지만, `DataScannerViewController` 는 화면에 붙는 순간 카메라를 켜고 그때 시스템이 권한을 묻는다. 그 덕분에 Scan 전에도 영상이 보여 미리 조준할 수 있는 것이라(§4), **"누르기 전 조준"과 "첫 Scan 때 권한 요청"은 VisionKit으로는 동시에 성립하지 않는다.** 조준이 더 중요하므로 원안의 권한 시점을 포기했다. 거부되면 카메라 자리에 안내와 `Open Settings` 버튼을 띄운다. 앱 안에서 권한을 되돌릴 수 없으므로 시스템 설정으로 보내는 것 외에 방법이 없다. **⚠️ 버튼은 아직 구현되지 않았다** (2026-09-21 확인) — 구현 계획의 Task 6 코드에서 빠졌고 리뷰에서도 걸러지지 않았다. 지금은 Scan을 누르면 `"Camera access is off. Turn it on in Settings to scan."` 문구만 뜨고 설정으로 가는 동선이 없다. 후속 작업으로 남긴다. `NSCameraUsageDescription`은 이미 `project.yml`에 있다.

**DataScanner 미지원** — A12 Bionic 이상(iPhone XS~)에서만 동작한다. iOS 17이 최소라 실질적으로 대부분 지원되지만 `isSupported` / `isAvailable` 확인과 안내 문구는 넣는다. 여기서 걸리는 기기가 나오면 접근법 B로 갈아끼울 판단 근거가 된다.

**인식 노이즈** — 2글자 미만이나 빈 문자열은 확정으로 치지 않고 계속 스캔한다.

## 7. 테스트 전략

**테스트 타겟을 신규 생성한다.** 현재 저장소에 없으므로 `project.yml`에 추가하고 `xcodegen generate`를 돌린다.

### 유닛 테스트 — 카메라 없이 검증

| 대상 | 검증 내용 |
|---|---|
| `StabilityDetector` | 같은 텍스트 유지 → 확정 / 바뀌면 리셋 / 2글자 미만 무시 / 타임아웃 발화 |
| `WordTokenizer` | 공백 분리, 구두점 제거, 빈 입력 |
| `ScanViewModel` | 상태 전이 — 가짜 `TextRecognizer` 주입 |

### 시간 주입

`StabilityDetector`가 시계를 직접 읽으면 "0.6초 유지" 테스트가 실제로 0.6초를 기다려야 한다. 느리고 불안정하다. **시간을 주입받도록 설계한다** — 테스트에서는 가짜 시간으로 즉시 검증하고, 실제로는 진짜 시계를 넣는다. 타임아웃도 같다.

`TextRecognizer` 프로토콜은 A/B 교체뿐 아니라 **테스트용 가짜 주입**에도 쓰인다.

### 실기기 수동 검증 — 자동화 불가

권한 요청 흐름, 실제 인식률(원서 × 조명 조건), 안정 판정·타임아웃의 체감 적절성, 버튼 위치가 손에 닿는지.

## 8. PLAN.md와의 차이 — 스캔 버튼 (유지로 결정)

PLAN.md §2 v4는 "폰을 움직여 박스에 맞추면 연속 인식"을 전제하고, 현재 화면 캡션도 "Move your phone to scan continuously"다. Claude Design 목업에도 하단 버튼이 없다.

스캔 버튼을 넣는 것은 **합의된 UX를 바꾸는 변경**이다. 의도하지 않은 인식을 막기 위한 선택이며, 실기기 테스트 후 버튼의 존폐를 재검토하기로 했다.

**결정 (2026-09-21, 실기기 테스트 후): 유지.** PLAN.md §2·§7을 버튼 방식으로 갱신했다. Claude Design 화면 목업에는 아직 버튼이 없으므로 **목업 갱신이 남아 있다** — 저장소 밖이라 디자인 쪽에서 요청해야 한다.

## 9. 실기기 검증 결과 (2026-09-21, iPhone 15 Pro)

| 항목 | 결과 | 조치 |
|---|---|---|
| Scan 전(`idle`) 카메라 영상 | **보인다** | 전제 성립. 가장 큰 설계 위험 해소 |
| 권한 팝업 시점 | 앱 실행 직후 | §6을 실제 동작에 맞춰 수정 |
| 인식·확정·단어 목록 시트 | 정상 | — |
| 빈 곳을 비췄을 때 타임아웃 안내 | 정상 | — |
| 안정 판정 0.6초 | 적당 | 유지 |
| 타임아웃 10초 | 너무 김 | **7초**로 변경 |
| 박스 바깥 블러 | 너무 불투명해 찾는 단어를 박스로 가져오기 어려움 | 블러 레이어 불투명도 100% → **70%** (50%·60%와 비교 후 결정) |
| Scan 버튼 | 유지 | §8 |

`.ultraThinMaterial` 은 이미 가장 얇은 시스템 재질이라 더 비치게 하려면 레이어 불투명도를 낮추는 수밖에 없다. 값은 `CameraView.outsideBlurOpacity` 상수에 있다.

**확인하지 못한 것:** 권한을 **거부**했을 때의 흐름(안내 문구와 `Open Settings` 동선)은 이번에 실기기로 보지 않았다. 앱을 지우고 재설치해 거부를 선택하면 재현된다. 원서 3권 × 조명 3조건의 체계적 인식률 측정도 하지 않았다 — 이번 결과는 사용자 체감 기준이다.
